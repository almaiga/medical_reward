# GRPO Garbage Output - Issue Identified and Resolved

## The Discovery

By comparing the logs, we identified **exactly where the garbage is generated**:

### Attacker Training Phase (WORKING ✅)
```json
{
  "phase": "attacker_training",
  "attacked_note": "A 52-year-old woman with HIV infection... An India ink preparation of cerebrospinal fluid is positive for Cryptococcus neoformans."
}
```
- Clean, proper medical text
- No garbage
- Proper modification made

### Assessor Training Phase (BROKEN ❌)  
```json
{
  "phase": "assessor_training",
  "attacked_note": "<think>useruserusera'*useruseruseruser..."
}
```
- Garbage output with repeating "user" tokens
- This attacked_note was **generated by GRPO during attacker training**

## Root Cause Identified

The garbage is NOT from:
- ❌ Our manual generation code (that works fine)
- ❌ The tokenizer (our patches help but aren't the main issue)
- ❌ The prompts we create (those are correct)

The garbage IS from:
- ✅ **GRPO's internal generation during training**
- ✅ GRPO generates completions when `attacker_trainer.train()` is called
- ✅ These completions use default generation parameters that don't work for Qwen

## The Problem Flow

```
1. attacker_trainer.train() starts
   ↓
2. GRPO takes prompts from ds_attacker (these are good)
   ↓
3. GRPO internally generates completions using the model
   ↓ [PROBLEM OCCURS HERE]
4. GRPO uses default/bad generation parameters
   ↓
5. Model generates garbage: "useruseruseruser..."
   ↓
6. Reward function receives garbage
   ↓
7. Garbage gets logged as "attacked_note"
   ↓
8. Assessor training uses this garbage
```

## Why Default Generation Fails for Qwen

Without proper configuration, GRPO's generation:
1. Doesn't set proper `repetition_penalty` → model repeats tokens
2. Doesn't set proper `temperature` → model gets stuck
3. Doesn't enforce EOS token properly → generation doesn't stop
4. Might not include BOS tokens → model doesn't know how to start

## The Solution

### 1. Configure Generation Parameters Explicitly

```python
generation_config = {
    "max_new_tokens": 1024,
    "do_sample": True,
    "temperature": 0.7,
    "top_p": 0.9,
    "top_k": 50,
    "repetition_penalty": 1.15,  # CRITICAL: Prevents "useruseruser" repetition
    "pad_token_id": policy_tok.pad_token_id,
    "eos_token_id": policy_tok.eos_token_id,
    "bos_token_id": policy_tok.bos_token_id,
}

common_cfg = dict(
    # ... other config ...
    generation_config=generation_config,  # Pass to GRPO
)
```

### 2. Keep Tokenizer Patches

The tokenizer patches still help ensure BOS tokens are included:

```python
policy_tok = patch_tokenizer_for_grpo(policy_tok)
```

### 3. Use vLLM if Available

vLLM has better generation handling:

```bash
pip install vllm
```

If vLLM is installed, GRPO will use it automatically with our configured sampling params.

## Key Parameters Explained

### repetition_penalty (1.15)
- **Most important for fixing "useruseruser" issue**
- Penalizes the model for repeating tokens
- Higher values (1.1-1.2) prevent repetition
- Too high (>1.5) makes output incoherent

### temperature (0.7)
- Controls randomness
- 0.7 is good for creative but controlled generation
- Too low (<0.3) → repetitive
- Too high (>1.0) → chaotic

### top_p (0.9)
- Nucleus sampling
- Considers tokens with cumulative probability up to 0.9
- Helps maintain quality while allowing diversity

### top_k (50)
- Limits to top 50 most likely tokens
- Prevents very unlikely tokens
- Works with top_p for better sampling

## Verification Steps

After running with the fix, check:

1. **Attacker training logs** - attacked_note should be clean medical text
2. **Assessor training logs** - attacked_note should still be clean (not garbage)
3. **Generation config output** - verify parameters are set correctly
4. **No "useruseruser" repetition** - this should be completely gone

## Why This Wasn't Obvious Initially

1. The error manifests during **assessor training** but originates during **attacker training**
2. GRPO's internal generation is hidden - we don't see it directly
3. The tokenizer patches seemed like the right fix (and they help, but aren't sufficient)
4. The research focused on tokenization issues, not generation parameters

## Additional Recommendations

### For Production Use

1. **Install vLLM**: `pip install vllm`
   - Better generation handling
   - Faster inference
   - Better EOS token support

2. **Monitor generation metrics**:
   - `completions/mean_terminated_length` - should be reasonable (not max length)
   - `completions/clipped_ratio` - should be low (<0.3)
   - `rewards/mean` - should increase over time

3. **Adjust repetition_penalty if needed**:
   - If still seeing repetition: increase to 1.2-1.3
   - If output is incoherent: decrease to 1.05-1.1

4. **Test generation before full training**:
   ```python
   python script/test_logic_tool.py --model_id your_model --num_examples 3
   ```

## Summary

The issue was **GRPO's internal generation using bad default parameters**, not primarily a tokenization issue. By explicitly configuring generation parameters (especially `repetition_penalty`), GRPO should now generate proper completions instead of garbage.

The key insight: **The garbage appears in assessor training but is generated during attacker training by GRPO's internal generation mechanism.**
